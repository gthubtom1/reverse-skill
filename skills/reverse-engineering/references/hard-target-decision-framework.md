# 困难目标决策框架

本参考资料补充原 `reverse-engineering` 阶段工作流。它描述决策和证据转场，不承诺存在一条能自动处理所有壳、虚拟化、反调试或动态代码的固定流水线。

## 目标

困难样本的主要问题通常不是缺一个工具，而是静态观察、运行环境和样本自保护互相影响。每次转场都要回答三个问题：

1. 当前证据说明目标处于哪一种阻塞状态？
2. 下一步选择会产生哪一种新的、可审查的证据？
3. 如果这一步失败，什么明确条件会让我们换方法？

原始文件只读保存。所有 dump、patch、解密输出和修复文件写入 case 工作区的副本，并保存输入身份、工具版本、命令、输出状态和 hash。

## 先分类，再决定动作

| 现象 | 首要假设 | 第一条证据路径 | 失败后的转场 |
|---|---|---|---|
| 入口、导入和字符串结构正常 | 未加壳或轻度保护 | 原生 triage → 静态 | 静态时间盒到期后转动态 |
| 入口很小、导入极少、节熵异常或 overlay 明显 | 压缩/加载器/壳 | 文件布局、导入质量、运行入口 | 运行时观察真实映射和解密阶段 |
| 业务代码只在运行后出现 | 动态解密/动态加载 | 模块加载、内存区段、关键 API | 以运行时快照回到静态分析 |
| 控制流呈 dispatcher/VM，基本块语义重复 | 虚拟化或控制流混淆 | dispatcher、opcode、状态读写 | 动态 trace 与小范围语义恢复 |
| 调试器、DBI 或虚拟机导致早退 | 反分析/环境检测 | 退出点、检测 API、时间/环境读取 | 降低观测扰动或更换隔离环境 |
| dump/修复后启动失败 | 自校验、布局或 IAT 破坏 | 失败时机、文件访问、校验函数 | 停止静态文件反复修补，转运行时旁路 |
| 网络/授权状态决定代码路径 | 服务端或环境依赖 | 请求、响应、状态迁移和错误变体 | 先建立离线状态模型，再决定是否动态观察 |

这些是候选解释，不是结论。样本身份和观测证据优先于壳名称猜测。

## 通用循环

```text
Triage
  → 建立样本身份、架构、入口、导入质量和初始假设
  → 选择 Static 或 Dynamic
  → 记录一次新的 Evidence
  → 检查是否回答了当前阻塞问题
  → 继续、回退、换工具或结束为 unknown
```

每次转场只记录改变后续动作的 `decision_delta`，其余状态通过原 scope、timeline、workitems 和 Evidence 引用继承。不要因为分析困难而创建第二套路由或第二套账本。

## 脱壳和保护层：实时判断边界

脱壳不是固定脚本。可以固定的是观察顺序和退出条件：

1. 保存原始 hash，识别格式、架构、入口、节/段、overlay、导入/导出和熵。
2. 判断静态结构是否足以支持当前问题；“导入很少”本身不是无行为结论。
3. 观察加载器、解密、模块映射、入口跳转和自校验发生的时间关系。
4. 只有出现足够证据时才选择 OEP、dump、IAT 修复或局部内存导出。
5. dump 后重新检查文件身份、入口、区段映射、导入/导出和可运行性。
6. 修复工具报错、修复后闪退或怀疑自校验时，记录失败证据并停止无穷静态修补；转运行时 API/内存观察。
7. 只有新版副本通过明确的结构和行为判据，才能称为“可分析副本”；否则保留 `packed`、`partial` 或 `unknown`。

壳名只是一个线索。UPX、商业保护器、自定义 loader、虚拟化和多层加载器可能共享表面特征，也可能需要完全不同的观察路径。不要把某次成功的 OEP 或断点地址迁移到另一个样本。

## 反调试和低扰动观察

困难目标可能检查调试器、DBI、Frida、断点、时间、线程、窗口、进程、驱动、虚拟机特征、网络状态或自身完整性。按以下顺序减少误判：

- 先记录早退点和退出原因，再判断是否为反分析。
- 优先做静态调用链、字符串、导入/导出、资源和配置观察，减少启动扰动。
- 动态时先使用最小观察面；一次只增加一种观测方式，并记录它可能改变的环境。
- 如果 DBI 或调试器触发退出，比较“无工具运行”和“最小观察运行”的差异；不要把无行为写成无功能。
- 需要修改检测结果时，只在授权隔离副本中进行，并记录修改点、原始字节和恢复方式。
- 观察到自校验、反篡改或完整性失败时，优先保存证据和切换读取路径，不对原始样本持续写入。

## 跨领域交接

困难样本经常跨越多个原有 PRIMARY：

- APK 进入 native `.so` 或运行时 dex：保留 APK 的 scope 和证据，再交给 `reverse-engineering`/IDA/radare2 的具体阶段。
- 网页脚本触发 WASM、Electron native addon 或远程状态：保留 JS 请求与 initiator，再进入对应脚本、WASM、native 或 protocol 入口。
- 协议字段由客户端二进制、APK 或 JS 计算：协议入口负责帧和状态，客户端领域负责算法实现，三方 Evidence 通过引用连接。
- 固件提取出 ELF、脚本、文件系统或协议：保留固件来源和提取身份，再交给对应领域，不重置原 case。
- .NET、Go、Rust、Flutter、IL2CPP 等格式：先使用格式专门入口建立身份和覆盖，再决定是否进入通用静态/动态阶段。

## 结束条件

困难目标可以在以下任一状态结束：

- 已得到足够证据并完成目标问题；
- 证据支持一个明确的下一阶段，但需要用户提供设备、provider、状态或授权；
- 当前方法失败，已记录失败证据并给出可执行的替代路径；
- 经过时间盒和分支比较后，结论仍为 unknown。

“没有崩溃”“文件存在”“工具退出 0”都不能替代行为证据。该框架不改变原路由、scope 门或 Evidence 契约。
