# HTTP：会话状态、重定向与重放判据

本篇为 [协议工作流](protocol-workflow.md) 增加 HTTP 状态语义，不把单条请求的字节正确当作整段会话可重放。引入批次：首批全领域增补；引入版本待独立 release PR 分配。方法仅描述授权环境的对照设计，本批未请求业务接口。

## DK-HTTP-01：Cookie 的作用域属于重放输入

**现象→判定：** 浏览器成功而脚本失败，不能仅凭请求体相同就排除状态差异。Cookie 存储与选择涉及名称、域、路径、有效期和安全通道；请求中的 Cookie 头不会完整携带这些存储属性，同名项也不一定代表同一存储条目。

**方法：** 从会话开始保留每次 Set-Cookie、跳转目标和随后实际发送的 Cookie，建立“收到状态→存储变化→下一请求”的顺序。重放时使用按域/路径管理的 cookie jar，再逐项比较浏览器发送结果；同时记录协议所需的防重放或 CSRF 状态，未观测依赖保留未知。核验应落到业务状态变化，不能只看 HTTP 200。

**版本/边界/反例：** RFC 6265 提供基础 Cookie 模型，没有覆盖现代浏览器全部 SameSite、分区和第三方限制，故需另记浏览器版本与策略。把 Set-Cookie 的属性拼进 Cookie 请求头、把所有同名值合并为一个字典键，均会丢失语义。Path 用于选择范围，不能充当安全隔离证明。

**方法评审：来源支持（来源正文已核，已检查适用条件与反例；未做本方目标实测）。** **本方状态：未复现。** 原文来源：[S14：RFC 6265 §4–5，存储与选择模型](https://www.rfc-editor.org/rfc/rfc6265.html)。

## DK-HTTP-02：重试与重定向必须保留方法语义

**现象→判定：** 重放工具报告成功，但服务端发生重复写入或收到不同方法，应先检查客户端的自动行为。RFC 9110 区分安全性、幂等性与状态码；幂等不表示没有副作用，连接断开也不证明服务端没处理请求。

**方法：** 在授权练习端逐跳记录方法、目标、请求体、响应状态与 Location；核对 303 的后续检索和 307/308 保持方法的要求。对可能写入的操作，先确定服务端是否有已知去重机制，再决定能否重试。验证同时看响应和实际业务记录，保留断连发生点及“不确定是否已执行”的状态。

**版本/边界/反例：** 面向 RFC 9110 的 HTTP 语义，具体库的重定向/重试策略需按版本确认；应用幂等键只有协议明确支持才可依赖。POST 超时后自动再发，可能创建两份记录；将所有 30x 一律改成 GET，则可能掩盖原流程差异。200 登录页、空业务结果或错误对象都不能充当业务成功。

**方法评审：来源支持（来源正文已核，已检查适用条件与反例；未做本方目标实测）。** **本方状态：未复现。** 原文来源：[S13：RFC 9110 §9.2.2、§15.4](https://www.rfc-editor.org/rfc/rfc9110.html)。
