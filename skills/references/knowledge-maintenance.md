# 知识维护：沿现有 references 与 journal 增补

本说明用于用户发起的知识维护和真实任务后的经验沉淀。先读 [AGENTS](../../AGENTS.md)、[RULES](../../RULES.md) 与 [CONTRIBUTING](../CONTRIBUTING.md)，沿原授权边界和维护链执行。客户端定位、安装注册与组件升级归安装仓库；本仓只保存客户端中立的方法、来源与经验，不改 REA/Spec Kit 原包，也不另建知识库、路由或后台采集器。

## 固定范围与比较增量

先固定维护模块、现有版本和原条目，查 [原经验索引](../field-journal/_index.md)；将候选与现有 references 对比，决定补充、纠错、变体或无增量。原文已经足够时不靠改标题新增一篇。优先查官方文档、源码与具名公开研究；二手说法回找原始出处。源码 main 和在线文档可能变化，仓外核对日志保存请求时间、最终 URL、内容摘要、相关章节与失败原因。

## 一个单元的最低要求

每个单元独立编号，写清现象、判定依据、可执行的方法、平台/版本、边界或反例、验证状态和真实来源 URL。引入批次与引入版本也要记录；尚未进入 release PR 时写“待分配”，不冒用当前 VERSION。方法是建议的实验设计时明确说明，不把作者报告的成功改写成本方实测。错误推断要解释为什么错，并给出恢复证据的方法。

“已验证”仅用于本方在明确目标身份、工具/平台版本、输入、实际输出和判据下复现的范围，保留正例与必要拒绝对照。“未验证”包括只读来源、缺设备、未运行或复现失败未闭环；失败观察可留证，但不据此宣布方法普遍无效。来源另记“原文已核/来源未核”：HTTP 200 还需检查正文支持；不可达或只有首页则标未核，不虚构章节或结论。

## 落盘与回写

稳定方法放所属模块的 references，实际执行经验才按 [原 journal 模板](../field-journal/_template.md) 记录，并按 [贡献流程](../field-journal/CONTRIBUTE-BACK.md) 匿名化。公开前移除客户事实、凭据、机器绝对路径和宿主运行时指令，引用公开原文而非整篇复制。来源研究不伪装成已完成项目，不为满足日志数量虚构 dated journal。

后续正常集成沿原模块 SKILL 的参考区、原 INDEX 生成机制和 journal/_index 更新导航；这些不是第二路由。本批写集只含新增参考文件，故未修改上述入口，不能声称自动加载已经接通。[本批来源清单](distillation-sources.md) 提供文件及单元定位，原存量不因本批加入就视为复核通过。

## 小批 PR、版本与检查

按主题拆小批 references/导航 PR，journal PR 仍遵守原白名单，最多四篇日志加 _index、共五个 Markdown 文件；版本和 CHANGELOG 走后续独立 release PR，关联各批来源。完整原 CI 必须保留并通过，不能删失败断言或用来源可达性代替技术验证。原 Git-index 链接检查依赖最终暂存内容；在用户禁止暂存的草稿阶段，只能另查工作树链接并如实标注覆盖边界。本批不暂存、提交或推送，不运行项目样本；完整 CI 与版本发布留给后续集成步骤，不能计作本批已通过。
