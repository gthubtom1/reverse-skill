# 已复刻项目跟随上游更新 / Upstream follow update

主路线是沿用我方独立实现与界面，调查新上游变化并重新验收。原件补丁/重打包若被明确选择，MUST 标独立成果类型，不能把旧二进制补丁适配称独立实现追版。

## 1. 唯一旧项目与原授权

MUST 先从用户当前成果项目恢复 `work/<case>/scope.md`、timeline/workitems、REA 完整 bundle/unknown 与 Spec Kit feature/tasks。跨项目搜索只能在用户明确给出的项目根内，根据产品/包身份、架构、版本链、旧上游摘要与原材料来源匹配；不扫描整机，不按目录名/产品名自动合并。

| 匹配结果 | 下一动作 |
|----------|----------|
| 唯一且身份/摘要可信 | 恢复原 case，进入三方固定 |
| 同名但包/架构/摘要不符 | 拒绝复用，保留新材料，记录身份冲突 |
| 两个或以上可信候选 | 列候选与差异，只暂停依赖身份的迁移，等待真正的项目选择 |
| 缺旧样本/构建/证据 | 明确缺件与未验证，继续独立可做的新材料分析，不假称完整恢复 |

授权 MUST 仍以原 scope 为准：新上游身份和本轮活动已被原授权覆盖才能 ACT；未覆盖必须先记录/取得范围扩展。MUST NOT 因“追版”自动扩大网络、设备或活动权限，也不为同阶段切换重复 case-init。

## 2. 固定三方

MUST 在原 notes 与原生 feature 文档引用三方身份，不建版本状态脚本/基线数据库：

| 标记 | 含义 | 必须固定 |
|------|------|----------|
| O | 旧上游 | 版本、包/架构、来源、项目内材料路径与 SHA |
| C | 我方旧独立实现 | commit、源码/锁依赖、包摘要、原 feature/任务/测试、我方 UI/品牌/特色与回滚 |
| N | 新上游 | 新版本、相同身份链依据、来源、材料摘要、环境 |

首次交付应已保留这些材料的 O/C 部分，以及原 bundle、需求→证据→测试、构建/安装/运行和恢复入口。首次缺项不能在追版中写成“旧版已完整验证”。

MUST 分三步比较：O→N 的新增/删除/接口及行为变化；O 已知行为→C 的实现/自有设计差异；C 自有设计对 N 的适用性。C 与上游语言/布局不同，MUST 比规格、行为与接口，不用字节 diff 推导语义迁移。

## 3. 只调查变化，保护我方设计

MUST 在原 notes 的 FR/接口/UI/构建引用表逐项记录：可复用、需适配、待确认、缺失、多候选、阻断。它们是审查结论，不是新任务状态；工作进度仍仅在 workitems 与原生 tasks。相似度、AOB 唯一命中、旧地址有效只能生成候选，业务语义未复核不能声称已复用验证。

MUST 由原 master-route 选择已有 `binary-diff/`（R15）调查 O→N，再由原领域 PRIMARY/REA 补 N 的新证据。不得复制旧 RVA/补丁或将 provider 内部分派当新 PRIMARY。后续规格/实现/验收用同一 master-route 的明确复刻阶段 Hint 进入 reconstruction，不建追版总控或第二路由器。

C 的 UI、交互、品牌、自有设计和构建默认保留。N 变化需要的适配必须说明对这些部分的影响。新功能 MUST 逐项做范围决定：用户已明确要求同步且原 scope 覆盖的直接进入新规格/验收；未明确的功能列出证据与选择，在真正边界上集中决策。MUST NOT 静默漏掉范围内新增，也不能强迫接收 N 的全部新设计。

## 4. 原生版本化 feature 与失效 proof

MUST 保留冻结旧版 spec/plan/tasks、旧 C 包和原始证据。沿原 Spec Kit feature 机制创建后继版本，在新 spec 中记录旧 feature 相对引用、保留功能、UI/设计约束、scope 内新增/变化、排除及未知。用原 tasks 补代码并运行 analyze/converge，不覆盖冻结旧版或重编号官方任务来掩盖缺项。

复用仍适用的我方源码、UI 与测试，只重做失效部分。每项“复用”必须说明哪些当前证据支持它；旧测试代码能复用，旧通过回执不能当 N 的验证。

MUST 提升变化需求的原 obligation_version，重算变化源码/依赖的 owner_sha256 与包摘要；fixture/verifier/比较规则/环境变化也使相关 proof 失效。旧 proof 留作来源，不参与本轮 readiness。由真实测试生产新 proof 再交 REA 生产 ledger/coverage；不得手工更改通过字段、复制 semantic ID 或在本清单重算 closure。

## 5. 回归、回滚与恢复

MUST 在 N 与新 C 之间实跑：旧功能同输入回归、本轮 scope 内 N 新增/改变行为、我方 UI/交互/特色、正常/错误/边界/状态/协议，以及干净构建、安装/运行与回滚。比较器规则和留出事先冻结，验证会话独立；错误变体必须能失败。任何失败不得覆盖旧 C 成品或移除旧回滚点。

默认沿用原 case。若确有独立授权/成果边界需要新 case，MUST 在原 timeline/workitems/notes 与新 case、后继 feature 用项目相对引用互链，不通过另一个项目登记库维护关系。阶段转移只追加 `decision_delta`，未变 scope/Evidence 用 `carry_forward_refs`。MUST 不修改原 Path 类型或 Evidence/Finding 状态枚举。

新报告 MUST 列复用、适配、新增、排除、未知、缺旧件与失效 proof，分别给“规格符合/原版对照/独立运行”结果，并写下一次恢复所需原 case、当前 feature/tasks 与 N 身份指针。

## 追版验收反例与状态

下表是必须在真实成果项目执行的验收要求；本目录只有交接机械单元测试，MUST NOT 声称这些领域场景已验证。

| 反例 | 应有结果 |
|------|----------|
| 产品同名但身份不符 | 拒绝恢复旧项目 |
| 多个旧项目 | 拒绝自动合并，给具体候选 |
| 缺旧材料 | 缺项保持未验证 |
| N 接口改变 | 新证据→新 feature 适配，旧 proof 不可用 |
| 上游换 UI | C 的已约定 UI/特色仍保留 |
| scope 内新功能漏入测试 | 验收失败，回原 tasks |
| 旧 proof/version/owner | 按适用性拒绝，不冒充新版通过 |
| 旧功能同输入回归失败 | 修复，保留失败与原回滚 |
| 新版构建/验证失败 | 不覆盖旧成品 |

端到端先用自有源码的合成 1.0→1.1 成果练习验证，再分别列 PE/APK、设备/补丁路线的真实验证状态。本目录的合成清单仅展示指针格式，无目标二进制、无真实目标，也不是这类端到端实验。
