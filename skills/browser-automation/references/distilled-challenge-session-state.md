# 验证码与风控挑战状态机（第二批）

本文件把验证码研究限定为“协议、状态和证据分析”。所有单元当前均为**未验证**；公开文档支持的是接口语义，不等于任何具体站点的算法、票据或风控参数已经复现。

## DK2-CAP-01：挑战生命周期必须和业务请求分开

**现象**：页面动作可能先创建 challenge，再加载脚本或 WASM，最后把答案、token 或风险结果带到业务请求。只观察最终 POST，无法判断 token 来自哪个 challenge，也无法知道是否绑定了 action、session、站点或时间。

**判定**：记录至少四类事件：challenge 初始化、用户/脚本提交答案、服务端票据返回、业务请求及业务响应。每条记录保留时间顺序、页面/iframe、请求方向、状态码和脱敏字段形状。把“票据有效”和“业务接受”分成两个结论。

**方法**：在自有或练习站点建立事件表，比较正常、缺 challenge、错 session、错 action、过期 token 和重复提交。对每一条请求保存 method、URL、query、header 名称、body 字段类型/长度和响应错误码；值只留合成占位或非敏感摘要。

**边界/反例**：Google reCAPTCHA 文档规定 response token 需要服务端校验，并且 token 单次使用、两分钟内有效；这能支持生命周期模型，不能推出其他厂商相同。HTTP 200 也不代表业务接受。

**状态**：未验证。**来源**：[Google response verification](https://developers.google.com/recaptcha/docs/verify)；原文已核，具体目标未运行。

## DK2-CAP-02：轨迹字段先做采样契约，再谈算法

**现象**：滑块、点选和轨迹参数通常包含时间、坐标、事件类型、窗口或页面尺寸等字段。不同采样频率、坐标原点、缩放比例和事件缺失会造成完全不同的编码结果。

**判定**：先确认字段的单位、采样窗口、排序、精度、压缩和是否绑定 challenge/session。记录浏览器 viewport、DPR、元素 bounding box、事件时间基准和页面重定向，不能只保存最终字符串。

**方法**：用合成轨迹做单变量实验：相同路径改变采样频率；相同事件改变时间间隔；相同坐标改变 viewport/DPR；分别观察请求结构和服务端接受结果。先建立字段模型，再定位序列化、压缩、签名或加密层。

**边界/反例**：事件捕获工具能说明浏览器观测到什么，不能证明服务端使用了哪一个字段。没有业务响应或接受/拒绝对照时，算法结论保持 unknown。

**状态**：未验证。**来源**：[W3C Pointer Events](https://www.w3.org/TR/pointerevents3/)；原文已核，未用于任何具体站点复现。

## DK2-CAP-03：风险分数、动作名和业务决策是三层

**现象**：风险服务可能返回 score、action、hostname、timestamp 或 error code，业务服务再根据阈值、账号状态和频率决定放行。只复现前端 token 不能证明注册或登录成功。

**判定**：分别记录风险服务响应、业务服务请求和最终业务结果。检查 action 是否和后端预期一致，hostname/包名是否匹配，时间窗口是否有效，重复 token 是否被拒绝。

**方法**：对测试账号建立矩阵：正常 token、错误 action、错误 hostname、过期 token、重复 token、风险分数边界。结果按“风险服务验证”“业务逻辑接受”“最终状态变化”三栏保存。

**边界/反例**：官方 reCAPTCHA v3 文档说明返回 score，由站点自行决定下一步动作；不能把 score 解释成跨站点通用阈值，也不能把单站点结果推广到所有风控服务。

**状态**：未验证。**来源**：[Google reCAPTCHA overview](https://developers.google.com/recaptcha)；原文已核，未验证具体阈值。
